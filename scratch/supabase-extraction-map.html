Supabase Extraction Map

Every place the application talks to Supabase, and what the replacement backend has to answer for. Swept across 143 API routes, 57 server actions, all pages, hooks and shared libraries.

All 143 API routes touch Supabase — directly or through a shared library. There is no subset to carve out; the dependency is total.

But the routes themselves are not the problem. They already are your API. What must be rebuilt is the layer underneath them: five Supabase services the route handlers call. Plus 11 places where the browser and client components skip the API entirely and query Supabase directly — those need brand-new endpoints that do not exist today.

01

The five surfaces to replace

Supabase is not one dependency here, it is five separate services wearing one SDK. Each needs its own answer in the new backend, and they have very different difficulty.

Auth 268 sites

GoTrue · cookie sessions

Cookie-based sessions via @supabase/ssr, refreshed in middleware.ts on every request. Methods in use: getUser ×234, signOut ×11, signInWithPassword ×5, signUp ×4, admin.createUser ×4, admin.deleteUser ×4, admin.updateUserById ×3, admin.listUsers ×2, getSession ×1.

Backend must provideSession issue/refresh/revoke, an admin user API, and a getUser that is cheap — it runs on every one of the 234 sites, so verify the JWT locally rather than round-tripping.

Database 785 queries

PostgREST · supabase-js

Every runtime query is a PostgREST call through supabase-js. 39 tables. Prisma is present but schema and migrations only — zero runtime usage, so the new backend can adopt Prisma outright.

Backend must provideEither a thin repository layer the routes call instead of .from(), or a PostgREST-compatible shim. Repository layer is the honest choice; the shim just postpones the work.

Storage 9 buckets

S3-backed object store

Upload, remove, list, signed URL, public URL, and create-bucket-on-miss. Private PII buckets are read through short-lived signed URLs minted by signStorageUrl(); signPiiUrls() walks 25 API responses rewriting them.

Backend must provideObject put/delete/list, signed-URL minting with TTL, and a public URL scheme. See the URL-shape trap in §10.

Realtime 8 subs

WebSocket · postgres_changes

Five tables are in the supabase_realtime publication: notifications, job_invitations, payment_requests, interview_rounds, job_offers. Subscriptions drive sidebar badge counts and SWR cache invalidation.

Backend must provideA change stream with per-row filters — or drop it. Every subscription here only triggers a refetch, so SWR polling replaces all eight with no feature loss.

Postgres logic 15 functions

RPC · triggers · RLS

Three functions called as RPC, twelve notify_on_* triggers that write the notification feed, three RLS helper functions, and several hundred RLS policies doing real authorization work.

Backend must provideThe triggers and RLS have no HTTP surface today — they are invisible in the route list and the easiest thing to leave behind by accident. See §7.

None of this appears in the route inventory, which is exactly why it gets missed. It runs in the database today and has to run somewhere in the new backend.

Triggers writing the notification feed

Twelve functions fire on insert, update and status change: notify_on_invitation_insert, notify_on_invitation_update, notify_on_invitation_status_change, notify_on_offer_insert, notify_on_offer_update, notify_on_offer_created, notify_on_offer_status_change, notify_on_round_insert, notify_on_round_update, notify_on_round_status_change, plus the notify_user helper. Notifications currently appear because the database wrote them. If the new backend writes invitations without reproducing these, the notification feed silently goes empty — no error, no failed request.

Row Level Security

Several hundred policies plus the helpers is_candidate, is_employer, is_mis_user. Of the 143 routes, 138 use the RLS-scoped session client and 124 also use the service-role client — 123 use both in the same handler. That split is the real authorization model, and it is only half written in the code.

What will bite you

Service-role keys are committed to git

supabase/migrations/20260523_02_schedule_dev.sql and …_03_schedule_prod.sql contain live service_role JWTs and the cron shared secret in plaintext, and both files are tracked. Anyone with repo access has full RLS-bypassing database access to dev and prod.

This is worth fixing today, independent of the migration — rotate both keys now, and do not carry the pattern into the new backend.

Stored URLs encode the Supabase host

The database stores full public URLs shaped …/storage/v1/object/public/<bucket>/<path>. privatePiiTarget() in src/lib/storage.ts parses that exact string to recover bucket and path. Change the storage host and every stored URL breaks unless you either keep the path shape or run a data migration over every resume, logo, image and certificate column.

Passwords are stored twice

users.password exists in the Prisma schema and Supabase Auth holds its own copy. resetPassword() writes both. Email verification and password reset are already custom — your own tokens, your own emails — so only the login check itself depends on GoTrue. Pick one store during the move and delete the other; carrying both into the new backend carries the drift bug with it.

Notifications appear by trigger, not by code

Nothing in the application inserts most notification rows — the database does, on twelve triggers. Write invitations from a new backend without porting those and the feed goes quiet with no error anywhere.

The cron routes look Supabase-free

/api/cron/expire-jobs and /api/cron/interview-reminders have no .from() and no auth call in their own files. Both are entirely Supabase-dependent through their lib imports. Any inventory built by grepping route files alone will miss them.

Suggested order

  1. Rotate the leaked keysBefore anything else, and unrelated to the migration.
  2. Replace the four client factories firstsrc/lib/supabase/{client,server,admin,proxy}.ts are imported by 205 files. Give the new backend an SDK with the same shape and the whole codebase keeps compiling while you swap implementations underneath.
  3. Auth, then middlewaregetUser() runs 234 times and on every middleware pass. Get it right and cheap before anything else moves.
  4. Port the thirteen shared librariesHighest leverage — routes change once instead of 143 times.
  5. Move RLS into the backend authorization layerThe biggest and least visible piece. 123 routes mix session-scoped and service-role clients in one handler; each one needs a deliberate decision, not a mechanical translation.
  6. Port the triggers as service methodsNotifications and the audit trail. Verify by watching the feed, not the HTTP status.
  7. Give the browser-direct calls real endpointsThe eleven files in §2. Two of them already have matching routes that simply are not being used.
  8. Retire realtime or rebuild itDeleting it is defensible — every subscription only triggers a refetch.
  9. Storage lastSelf-contained, and it is the one that needs a data migration if you change the URL shape.
